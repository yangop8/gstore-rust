## C. 代价式查询优化器 ★中价值 —— ✅ 已完成

- **候选与启发式**(`src/query/candidates.rs` + `planner.rs`):精确候选生成(常量边求交+选择度传播)、NodeScore启发式、采样基数估计、卫星点延后。模式数>14时由`planner`贪心定序兜底。
- **DP优化器**(`src/query/optimizer.rs`):
  - **左深DP**(`n·2ⁿ`子集DP):`dp[S]`=物化`S`内模式的最优代价,逐个追加连通模式,产出最优左深pattern序,替换原贪心序。
  - **二元(bushy)连接**(`3ⁿ`子集划分DP = gStore `ConsiderBinaryJoin`):枚举把`S`划成两个连通半区的所有方式,得到最优二元连接树`JoinTree`;当其严格比最优左深更省时,由engine的hash-join树执行器(`eval_join_tree`)执行,否则仍走左深流水线。
  - **System-R代价模型**:模式基数取自要扫的索引区间大小;连接输出基数=`|A|·|B| / Π max(NDV_A(v),NDV_B(v))`,NDV(distinct值数)取自谓语统计`pre2sub`/`pre2obj`并用精确候选集收紧。
  - **plan_cache**:DP表本身即子计划代价缓存;evaluator另置结构同构BGP的plan缓存(子查询/重复BGP复用枚举结果)。
  - 验证:`tests/dt_optimizer.rs`(bow-tie二元连接端到端)+ LUBM部分查询实际走bushy且计数全对。
- **后续可优化**:跨查询持久化plan cache、直方图/相关性估计、topk优化(原版`topk`/`DFSPlan`)、命名物理join算子枚举。

### I.5 并发与服务器

- 内存 `ConcurrentDb` 上,释放了某个词的删除在已发布快照共享 interner 时复制整个 interner(`Interner::retire` 的 `Arc::make_mut`,O(词数))。插入新词从 Round 2 起就有同样的复制。去掉它需要分块或持久化的 interner、给 interner 也加 spare copy(像 `TripleStore::keep_spare_copies`),或推迟释放直到 interner 不再共享。先用 `ConcurrentDb` 的更新延迟测试驱动(`dt_cow_store`)测量。Update (review-fix campaign, conc#2 follow-up, merged from r4-concurrent): the first brand-new term interned after a publish copies that term space's interner, O(terms) — about 0.4 ms per commit or `write()` at 20,000 entities in a debug build; a spare interner replayed with the terms interned since (O(new terms)) would make such commits flat. It changes `src/dict/mod.rs`, an interning hot path (bench-gated).
- `ConcurrentDb` 包着 Stream 库时存活期间不释放 id:基准快照(`VersionView` 的后备)读共享的磁盘字典,需要 pin。要释放,基准就得能解析自己的 id(一份字典副本,O(词数)),或用 D2 的版本化读。
- 每库的 `[query]` 设置改为语句开始时读取的无锁单元(R3 review):现在 `read_synced` 在库一直忙于读时延迟应用新设置。
- `/api monitor` / `schema`:从未为本实例算过统计的库仍在请求路径上计算(共享守卫,排在后面的写者要等它)。Update (review-fix campaign, gapi#17): an unloaded database's `monitor` / `schema` statistics are now cached until a walk of its directory shows its files changed; a loaded database whose statistics were never computed still computes them on the request path (this item).
- 事务快照 CSR 的取消延迟是一个谓词的 `so_by_p` 读(`rdf:type` 这样数百万三元组的谓词仍整个读完才看到标志)。See analytics#6 (J.7): a streaming per-predicate `TripleSource` read could also let the build poll inside it.
- 单库 / 多库服务器的重入注册表只拒绝同一库的第二个守卫;同时持有两个不同库的守卫不拒绝(没有路径这样做,C8 禁止)。

### J.2 Storage kernel, on-disk formats and the disk layout

- **disk#7** (deferred, info; D8 with D2 / D7) — VList compression and `IsArray` are not used by production builds but stay on the disk store's read path (`src/kvstore/store.rs`) and in the documentation. *Reason:* see J.1. (plan)
- **disk#9** (partial; D7) — the write-ahead log still records no identity of its file. Binding them needs a new WAL framing behind a format-registry feature bit, which would make every new file unreadable for older binaries (an older binary would discard a log in the new framing as torn). *Reason:* not required — the cross-process pager lock, the single path rule (`Pager::wal_path`, `Pager::remove_with_wal`) and the checked, log-first removal close the failure paths the review names (a foreign log beside a fresh file, two openers). (r3-storage-kernel)
- **disk#9, durability#1** — `remove_other_layouts` (`src/db/persist.rs`) removes `<file>` and `<file>.wal` but not a staged `kvstore.kv.wal.tmp` when a directory switches to another layout. Harmless: a staged log is never replayed, and the next open of a disk database there removes it. The four duplicated WAL path rules listed with it were unified by r3-storage-kernel. (r1-storage-failstate)
- **durability#8** (optional; D9) — the directory fsync after removing the WAL is not needed for correctness: the next commit's rename-time directory fsync persists the removal, and a log that reappears after a crash is always the batch the file already holds (its replay is idempotent). Dropping it saves one directory fsync per commit: the rename plus the two directory fsyncs a commit now makes cost about +0.4–0.6 ms per single-triple disk commit (`target/release/gstore-bench ci --baseline bench/baselines/smoke.json`, base `7bbf4ae` against the branch on a loaded 4-vCPU machine; report-only update medians, e.g. lubm-like insert 1.285 → 1.878 ms). (r1-storage-failstate)
- **disk#15** (partial; D8) — opening any pager file still needs write access and replays / creates as a writer would. A read-only `OpenMode` for `Pager` (no create, no WAL replay, refused writes) is an API addition left for later; `open_disk` now refuses a missing or empty file, the half that changed behaviour silently. (r4-storage-format)
- **disk#4, disk#15** — a `vstree.kv` whose header is damaged, or which is empty, now fails `Database::open` of the disk layout with "remove it to rebuild the index". The file is a derived index: `load_disk_stream` / `load_disk_materialize` (`src/db/persist.rs`) could treat a refused `vstree.kv` as stale and rebuild it, as they do for a missing one. (r4-storage-format)
- **db#4** (partial; §I.1 D6) — the in-memory VS-tree is rebuilt after a clear and folds inserts and inferred triples, but the Stream-mode `vstree.kv` is not rebuilt in session after a clear, an insert or reasoning, and an out-of-core tree (Materialize mode's `vstree.kv`, `use_streaming_vstree`) is still dropped from use by the first insert (only a clear or a reasoning run rebuilds it in memory) — the non-incremental paged tree. *Reason:* an operation-end rebuild for Stream mode would need commit points inside a statement. (r4-db-graph)
- **robust#11** — reads of an overflow chain are bounded, but `kvstore::overflow::free_chain`, which `DiskStore::compact` runs over the previous index, still follows a damaged chain unchecked: a cycling chain frees a page twice and leaves the free list cyclic. A visited-page bound (or a check against the free list) would close that write path. (r4-storage-format)
- **gap-accel-soundness#4** — a saturated disk-layout `pred_stats` count stays at `u32::MAX` across deletes until `DiskStore::rebuild_stats` recounts (nothing calls it on demand besides the open of a pre-statistics file). *Reason:* widening the record to `u64` needs a feature bit (D7), not worth one at this scale (2^32 triples of one predicate). (r4-storage-format)
- **disk#3** (Stream mode) — `DiskTriples::free_ids` leaves the named-graph check to its caller (`db/reclaim.rs` checks `NamedGraphs::node_refs` / `pred_refs` first); the store-level quad reference counts of `DiskStore::free_key` could serve as a second safety net. (r3-storage-kernel)
- **db#1, robust#4, durability#3** (D7) — a stale but decodable `named.bin` (an older copy restored beside a newer `meta.bin`) is not detected. Recording the quad count, or per-member checksums, in `meta.bin` behind a format feature bit would detect it. *Reason:* needs a format change. (r1-durable-ack)

### J.3 RocksDB

- **gap-rocksdb-exec#1** (partial; H-11 follow-up) — auto-commit UPDATE requests and `insert_sources` / `remove_sources` are journaled statements, but REST `/batchInsert`, `/batchRemove` (`handle_batch_insert` / `handle_batch_remove`) and REST `/upload` into a loaded database (`handle_upload`) still apply one `try_insert_triple` / `try_remove_triple` per triple, each its own RocksDB write: a crash keeps a prefix. (r1-rocksdb)
- **gap-rocksdb-exec#1, gap-rocksdb-exec#4** (round-1 review) — a live rollback of a very large transaction (`replay_kept_journal`, shared by `rollback_keeping_journal` and `rollback_uncleared_journal`, and the retry of a failed one) still reads its whole journal into memory and keeps it until its terms are checked; the bounded, resumable chunked replay with the pending reclamation range covers the recovery at open only, and the same chunking would apply. (r1-rocksdb, r1-integration)
- **gap-rocksdb-exec#2** — REST `/checkpoint` and `/api checkpoint` call `DbSlot::save` (a commit point: WAL fsync); `Database::checkpoint` also flushes the memtables. Route explicit checkpoints there if a flush is wanted. (r1-rocksdb)

(r1-rocksdb)
- **gap-rocksdb-exec#3** (§I.1 D4) — native RocksDB snapshots, so that `/begin` copies nothing, stay open; see the D4 row. (r2-txn)
- **gap-txn-lifecycle#3** (M2; D3) — the RocksDB commit outcome is covered at the library level (`src/txn_commit_tests.rs`, the `cfg(test)` journal failpoint) but not by an HTTP-level test: no OS-level injection hits the journal deletion deterministically, and the failpoint is not reachable from integration tests. (r2-txn)
- **db#18** (remainder) — an id inside its space (below 2,000,000,000) still sizes that space's slot vector (24 B per id) when the RocksDB dictionary loads; `try_reserve` turns a refused request into "corrupt RocksDB dictionary", but under memory overcommit a corrupt id near the bound still costs that allocation. ### J.4 Durability: logs, backups, layout replacement and locks

- **durability#1** (§I.1 D12) — a failed commit of an update larger than the page cache can still leave a prefix of it durable; see the D12 row. (r1-storage-failstate, r1-rocksdb, r2-txn)
- **durability#6, robust#10** — owed redo / update-log records live in memory without a bound while a log stays unwritable and direct-API writes go on, and they are lost if the `Database` is dropped before an append succeeds (`Database` has no `Drop` flush; a later increment chain then has a gap that nothing reports). A cap with a sticky "gap" mark cleared by the next full `backup()` would bound it. (r3-db-redo)
- **durability#6** — the logs are appended after the commit point, so a crash between the two (one `write` and one `fdatasync`) leaves a disk or RocksDB store holding a committed statement its logs lack, and the next `backup_incremental` misses it silently (the opposite order would log statements a crash then undoes). A two-phase record (prepared before the commit point, confirmed after) or a commit sequence number in the store would close the window. (r3-db-redo)
- **durability#6** — torn versus corrupt: a defective record is torn unless a whole record (complete, checksum right) follows it, and the appender cuts at the record's start. Two contrived cases remain: a torn update-log statement whose own text holds a complete record with a valid checksum (a line `REC <n> <n> <len> c=<crc>` followed by exactly `<len>` matching bytes) is reported as corruption instead of skipped; a record whose length field was damaged to run past the end, followed only by a torn record, is skipped with the torn tail instead of reported. A per-append marker or a log-level sequence number would remove both. (r3-db-redo, corrected by r3-integration)
- **durability#6** — an auto-commit UPDATE that fails part-way has its applied (committed) part in the redo log but not in the statement-level update log, which cannot express a partial statement. (r3-db-redo)
- **durability#6** — the "logs in doubt" mark is session state, like the backup checkpoint (`backup_offset`), not persisted: after a reopen the chain needs a full `backup()` anyway. A RocksDB transaction whose journal was deleted but whose WAL sync failed is in doubt rather than classified (RocksDB does not say whether the batch is durable). (r3-integration)
- **db#8** — `replay_*`, `backup_incremental` and the appender's first scan read the log into memory; a streaming reader would bound memory for very large logs. The scan runs once per session and `backup_incremental` reads only `[checkpoint, end)`. (r3-db-redo)
- **parser#8, parser#5** (library logs) — update-log replay goes through the SPARQL parser (`parse_logged_update`, which still calls `check_request_size`), so a process that installed `[upload] sparql_max_size` (gserver, gbuild) would refuse a logged statement longer than the limit; an old-shape redo record is read through `ntriples::parse_str`, bounded by `rdf_max_token_size`. Neither log is used by a binary, so nothing was changed. (r3-integration)
- **db#13** — `Database::restore` says a snapshot backup "is never written", but `open` takes the backup directory's lock (writing `LOCK`); `restore_incremental` no longer does. (r3-db-redo)
- **db#14** — `checkpoint()` / `save()` of an in-memory database inside a transaction still save the live state (documented on `save`); only `backup()` refuses. (r3-db-redo)
- **durability#15** (partial; also durability#9, durability#16; D3) — the stage+swap primitive landed; what remains of the layout-replacement redesign: (1) the replacement paths still differ in shape: the bulk disk install (two files in place, 8 steps, `bulk::commit::install`, shared with the incremental disk build), the bulk RocksDB install (`bulk::rocks_sink::install`, duplicating `StagedDir::install`'s "where did the swap stop" recovery), the RocksDB save into another directory (`save_locked` calls `install_staged_dir` directly), the restore (`install_staged_dir_as` with `RESTORE_SWAP`) and the snapshot set (`SnapshotWriter`); one layout-replacement API owning the lock, the staging, the install steps and the recovery per layout would subsume them. (2) `backup_dir` / `copy_disk_files_to` stay file-by-file copies made safe by order, not a staged swap: `gbackup`'s positional form writes into an existing directory that may hold files a swap would delete, so that contract must change first. (3) The flush-failure divergence (`DiskSink::flush` retried where `DiskTriples::commit_point` poisons) was durability#16's and is fixed. (4) The first decision on a legacy shadow is still by mtime (`>=`), the only information a legacy build left; `copy_disk_files_to` over a directory holding a snapshot written in the same second (whole-second timestamps) would take it for a newer shadow — the bulk install's `newer_than_snapshots` step is not applied there (low; two unlikely conditions). (5) Two discard variants remain: `discard_dir` (`STORE_SWAP` names, `rocksdb/`, a staged `.new`) and `discard_db_dir` (`DROP_SWAP`, whole database directories). (6) Leftover `<name>.db.drop-old` directories are removed by the next drop of the name, not swept at server start; the `/api drop` of a missing database removes a leftover without the name's busy claim (it only touches the `.drop-old` name). (7) durability#9 / durability#15 (low, older than the campaign): a file-level copy (`backup_dir`, which `gbackup` uses for a directory holding `kvstore.kv` without opening it) of a directory with an unreconciled legacy shadow (possibly with `SHADOW.apply`) keeps neither the mtimes nor the marker, so the copy opens as the store's state where the source opens as the shadow's; it needs an interrupted snapshot save over an on-disk database followed by a file-level backup before any open. Fix direction for the redesign: reconcile the source first (open it under its lock) or refuse such a source — `stage_restore` also copies a backup with `backup_dir`, and a restore must not write into the backup. (r2-layout-cli)
- **durability#12, bulkcli#15** — the bulk install's `COMMIT` marker stays an advisory record (D7: no format change); a roll-forward recovery from a marked staging area was not added because nothing would use it (the next build replaces the staging area anyway). (r4-cli-config)
- **bulkcli#6** (D8) — `Database::restore_from_zip` (`grestore x.zip`) and the `/api` restore still unpack into the fixed `<target>.unzip-tmp` (`ScratchDir::fresh`, removing what is there). Kept: both run under the database's restore lock / the `/api` name reservation, so bulkcli#6's race does not apply, and `fresh` removes a crashed restore's leftover at the next one, which `ScratchDir::create_unique` (a new name per run) would leave behind without a sweep. (r4-integration)
- **durability#11** — `fsutil::discard_dir` renames a directory aside only when the target is one; the rule-directory helper (`remove_rule_dir`) handles a non-directory itself (a dangling link is removed, anything else is an error), while the other `discard_dir` callers (database drops) keep their behaviour for a non-directory at the target. (r4-integration)
- **durability#11** — `Database::save` of a detached database with in-memory rules holds `persist_lock` and the directory's writing exclusion, which contract C8 orders after the rule lock, so it takes the rule lock with a try-lock and is refused (before anything is written) while another operation holds it. Taking the destination's rule lock in `save` before `persist_lock` (`src/db/persist.rs`) would let it wait instead. (r4-ext-docs)
- **db#11** (follow-up) — within one process, opening a snapshot directory (its recovery discards staged snapshot members) while another thread saves into that directory is not serialized by the writer exclusion; only saves are. The servers never do this (per-name reservations); the module docs make it the library caller's job. (r2-dirlock)
- **DirLock and `fork`** (r3-storage-kernel's request; no review id) — the reported race (the last holder dropping the locked descriptor without `unlock()`, so a child spawned meanwhile keeps the lock until its `exec`) does not exist in `DirLock`'s `Drop`, which unlocks explicitly before the file is closed (code older than the campaign). What remains is the acquire retry path of `DirLock::acquire` and `SideLock::acquire` (`Ok(()) if !still_named_by(..) => continue`): it drops a locked file that the path no longer names without `unlock()`. No contender reaches that file through the path, so at most a process that opened the old file before it was replaced sees a spurious conflict; an explicit `unlock()` before `continue` would remove it. (closing check)

They stay unpersisted by design (library API); compiling them to the `reasonManage` / `INSERT … WHERE` path and persisting them is the refactor the review suggests. (r4-ext-docs)
- **ext#6** (deferred; D7 / D8) — the `reasonManage` ledgers do not scale: string sets are copied several times, and every execute / disable rereads all ledgers under the database's write lock. A ledger storage redesign (sorted streamed files or an owner-count index) would change the `reasonManage` on-disk format without any confirmed failure. (plan)

### J.8 HTTP servers, REST and `/api`

Request handling and framing:

- **design#1, http#5** (D3) — request parameters are parsed in two places: `server::Request` (URL + form body, Content-Type aware) and `gapi::params::Params`, which keeps upstream's guessing (a body containing `=` is a form, one starting with `{` is JSON, whatever the Content-Type) for wire compatibility with the upstream SDKs; unify only if the upstream clients' content types allow it. REST does not read multipart form fields (it never did). (r1-http-surface)
- **sec#16, http#14** — an unsupported transfer coding is answered `400`, not RFC 9112's suggested `501`, and a request that misses its deadline `400`, not `408`: `write_response_ext` has no reason phrase for 501 / 408 (it would print `501 OK`). Add both phrases and switch `BadRequest` to them. (r1-ingest-framing)
- **http#3** — the read deadline below rustls is enforced by `ConnSocket`, which reads the deadline the request reader publishes in a worker-thread-local `ReadClock`, because the readers are generic over any `BufRead` and their signatures were kept. Driving `complete_io` manually would need the TLS stream type in `serve_connection` or a new trait bound; a refactor threading a connection context through `read_request` could carry the deadline explicitly. (r1-ingest-framing)
- **sec#3** — `max_conns_per_ip` keys IPv6 peers by their full address, so a client rotating addresses within its prefix is not held to one count; keying by /64 is an option if IPv6 floods matter. (r1-ingest-framing)
- **sec#11** — buffered responses (envelopes, query results) still go out as one head-plus-body copy from `write_response_ext` (one write, so a kept-alive connection never waits on Nagle) and gzip compresses into a further buffer; bounded by `max_output_size`. File downloads and, since r3-rest-parity (http#11), REST `/export` are streamed. (r1-download)
- **gapi#4** — a streamed download with `Accept-Encoding: gzip` is sent identity-encoded: on-the-fly compression needs chunked framing, which an HTTP/1.0 client cannot take, and the request version is not kept in `Request`. (r1-download)
- **gapi#4, sec#3** (round-1 review) — there is no per-client share of `download_max_concurrent`: the send deadline (`min_body_rate`) bounds how long one slot is held, not how many slots one client takes. (r1-integration)
- **parser#8** — `sparql_max_size` is checked when the request text is parsed, after the HTTP layer has buffered the body (bounded by `upload_max_body_size`); refusing a `/sparql`, `/query` or `/api` body longer than `sparql_max_size` before reading it would save the buffering. Not an amplification. (r3-parser)
- **ext#12** — a plain-HTTP request to `gserver --tls-cert` is not refused at once: the client waits about 31 s (the read timeout) for the close. A prompt close or a clear-text 400 in `src/server.rs`'s TLS accept path would help users who forget `--tls`. (r5-console, r5-integration)
- **ext#12** — the pre-body admission of the upstream `/api` payload route (`src/preauth.rs`) takes credentials from the URL query only, not a session token, so a session-authenticated `/api` body stays under `preauth_max_body_size` (64 MiB), as bodies carrying the password always did. (r5-console, r5-integration)
- **sec#1, gapi#1** (informational) — the `/api` body is still parsed before authentication: upstream's body-wins rule for duplicated parameters needs the body first. Bounded by the pre-authentication cap, the body budget and the parameter bounds. (r1-ingest-caps)

Security and authentication:

- **sec#9** (D8 residue), **gapi#5, sec#7, http#6** (round-2 review) — the `/api` IP allow / deny lists and the login lockout key on the TCP peer (the lockout per account and address, /64 for IPv6), so behind a same-host reverse proxy every client is `127.0.0.1`. Keying them on a trusted `X-Forwarded-For` hop needs a configured trusted-proxy list and the same client address on every lockout path (REST Basic, `/login`, `/api`, the pre-body check): a new configuration decision (a new `conf.ini` key), not a local fix; mitigated by the known-good-account exemption of the address-wide lock. (r1-http-surface, r2-limits-auth, r2-integration)
- **sec#7, gapi#5** — the lockout is asked before the password hash and told the outcome after it, so attempts of one account and address sent concurrently all pass the check before the first failure is recorded: a burst of up to `thread_num` guesses (bounded by `max_conns_per_ip`) per lock window instead of one; concurrent PBKDF2 verifications are not bounded either. Closing it needs an in-flight count per key on every password path (refuse while count + in-flight checks reach the threshold). (r2-limits-auth)
- **sec#7** (note) — session-token requests are not throttled: a token is 128 random bits, nothing to guess, and invalid tokens do not count towards the lockout, so expired sessions behind a NAT lock nobody out. (r2-limits-auth)
- **infra#3** (D1 residue) — the upstream `/api` protocol keeps its state-changing `GET` operations with credentials in the URL (`GET /api?operation=drop&username=…&password=…`); the Origin guard covers state-changing methods only, so a web page that knows a password can drive `/api` through a visitor's browser with an `<img>`. Kept for wire compatibility; it matters with `allow_default_root_password=on`. A later change could refuse state-changing `/api` operations over `GET` behind a compat switch. (r1-http-surface)
- **gapi#7** — `ipmanage` does not refuse an allow list that would lock out the calling address: a new refusal that needs a policy decision (proxied or trusted-local callers, root knowingly replacing the list); upstream writes any valid list. The silent-emptying cause is fixed, and an empty `ips` was already refused (1003). (r1-durable-ack)
- **sec#1** — an authenticated upload past the pre-authentication cap is hashed twice: the pre-body hook verifies the head credentials (one slow PBKDF2) and the handler verifies them again. Passing the verified identity needs a field on `Request`. (r1-ingest-caps)
- **gapi#6** (remainder) — `grant` / `revoke` / `drop_user` / `clear_privileges`, the database-registry saves and `IpFilter::save` still fsync under the state lock (no hash involved; one fsync each), and so does the legacy-hash migration in `UserStore::finish_check` (rare). (r2-limits-auth)

Uploads, downloads and files:

- **sec#1, gapi#1** (C-2 remainder; D3) — a multipart upload is kept as `Request.body: Vec<u8>` and its file part copied out (`UploadedFile.data`), so an upload costs about twice its size in memory (the body is charged to the budget, the copy is not; both are bounded). Streaming an authenticated upload to a temporary file under `upload_path` needs a streaming body type in `server.rs` and an owned-body path through `gapi::Params`. (r1-ingest-caps)
- **sec#1, gapi#1** — the body budget counts the bytes received, not the `Vec`'s capacity (`read_body` pre-allocates up to 1 MiB of an announced body and a growing `Vec` may hold up to twice its length), so it bounds memory within about a factor of two. (r1-ingest-caps)
- **sec#14, gapi#14** — owner records are kept per file, not in a transactional registry: the quota check is not atomic with the upload, so two concurrent uploads of one user can both pass it. Accepted for a soft quota. (r1-download)
- **sec#4, sec#14** — owner records are written atomically and durably, but a crash between creating a file and writing its record can leave a file without one; it fails closed (root / admin only, kept by the sweep like an operator file). (r1-download)
- **gapi#14** — a refused `build` / `batch*` source `file` answers "refused", a missing one "not exist": a user holding `update` somewhere can test whether another user's upload with a guessable name (`<stem>_<YYYYmmddHHMMSS>`) exists, without reading it. Exports and query results have random names, and a download answers `FileNotFound` either way. (r1-download)
- **gapi#13** — the orphan rule for `<root>/tasks` assumes one server per root (gserver's pid-file check enforces it); two `ApiServer`s on one root in one process would remove each other's spilled results. (r1-download)
- **gapi#11** — streaming `format=file` removed the serialization multiplier, but the `ResultSet` is still materialized and uncapped for the file formats, so a huge result costs its own size (1.4x the file in r1-download's measurement); streaming rows from the evaluator into the file is a larger refactor of the query path. (r1-download)
- **design#4** (divergence) — REST `/upload` with `format=nquads` or `trig` flattens every named graph into the default graph (`parse_rdf` uses `parse_str_triples`), where `/api` `batchInsert` / `build` keep quads in their graphs; routing quads needs the `insert_sources` path. Only the REST `/export` → `/api` `build` round trip is checked by `tests/rest_api_parity.rs`. (r3-rest-parity)

Asynchronous operations, tasks and logs:

- **gapi#12** — `max_pending` is global: one user can still fill the runner queue with expensive asynchronous operations (no per-user quota); the callback queue is bounded per user and by bytes, but not per callback host. (r2-limits-auth, r2-integration)
- **durability#2** — `run_query_job` ends the task of a non-durable update as succeeded (`task.set_ok(out.is_ok())`; the update returns `Ok` with a warning, mapped to Persist only for the reply and the log). Not visible on the wire today (`operationTaskList` reports both as finished, status 1); align it when task state becomes visible. (r1-durable-ack)
- **gapi#18** (remainder) — `querylog` / `accesslog` still read the day's log file whole per request (bounded by one day and the retention count); an index like the transaction log's would make them incremental. (r4-api-hygiene)
- **gapi#19** (partial, info) — `SysDb::sync_with_disk` has no runtime caller (only tests) although the sysdb module docs say the registry is reconciled on demand, and the test-only `__asyncTest` operation is registered in production builds behind a process-wide flag (`src/gapi/ops_task.rs`, `src/gapi/tasks.rs`). `Params::to_redacted_json` is linear now (a public helper, D2), and `TxnState::Aborted` is used by `ApiLogs::abort_stale_running`. (r1-ingest-caps)
- **`gapi::tasks::spawn_pool_thread`** (no review id) — it drops the handles of pool threads whose `is_finished()` is true when it starts a new one; such a thread may still run its thread-local destructors and so outlive a later `serve_forever` by that much. Joining those handles outside the lock fixes it; no test can observe the window without a hook in the runner's thread exit. (r4-integration, r5-integration)

Transactions:

- **sec#10, robust#5** (round-2 review; D3) — a failed multi-operation UPDATE inside a transaction keeps its applied operations in the transaction (and says so). Undoing back to the statement's start needs a savepoint in `Database`'s undo log covering every layout (the Stream-mode overlay, the RocksDB journal, minted terms). (r2-integration)
- **gap-txn-lifecycle#1** (D3) — a transaction whose owner was deleted is detected lazily (next begin, the background pass, or the next request after a transaction request found it orphaned); a plain non-transactional write in between is still refused. Detecting it at deletion time needs the user-management code to arm the reaper (`ApiInner::txn_reap.arm(0)` after a user is deleted). (r2-txn)
- **gap-txn-lifecycle#4** — single-database mode (`gserver DIR`) has no unload / load: a database broken by a failed commit needs a server restart (unchanged by design). (r1-storage-failstate)
- **design#4** (family; D3) — the REST and `/api` transaction lifecycle code is split across `http_api.rs` (handlers, registry) and `gapi/ops_query.rs` (envelopes); a shared lifecycle module remains a refactor candidate, no behaviour depends on it. (r2-txn)

Operation layer and duplicates:

- **design#4** (partial; D3) — one protocol-neutral implementation of build / load / unload / backup / restore / drop / export / batch / users for REST and `/api` (e.g. `src/service/`, with `ApiInner`, `ApiState`, `DbCell`, `DbSlot`, `ReadSnapshot` moved out of `src/http_api.rs`) was not built; two copies of restore, backup, drop, load and build remain. Every concrete divergence the review and the parity suite found was fixed and pinned in `tests/rest_api_parity.rs`. Deliberate differences, documented on the handlers: REST `/build` rebuilds an existing database (`/api` refuses), REST `/drop` always deletes, REST `/restore` needs a path and leaves the database loaded, REST `/export` of a database in a transaction writes its committed state (`/api` refuses, as upstream). (r3-rest-parity)
- **design#4, http#11** — `ReadSnapshot::write_export` (REST export of a transaction's snapshot) duplicates the statement loop of `zipio::write_export`; a `TripleSource`-generic writer in `zipio` would serve both. (r3-rest-parity)
- **design#17, design#4** — REST accepts database names of 1–2 characters (`valid_db_name`) that `/api` operations refuse (`check_db_name`, upstream's "length at least need 3"); both surfaces list them, but one name rule for creation is still to be chosen (refusing them on REST is a visible change for existing databases). (r4-api-hygiene)
- **gapi#15, design#13** (partial) — duplicates kept, with reasons: the `civil_from_days` date math in `gapi/ops_query.rs`, `sysdb.rs` and `query/value.rs`, and the UTC-versus-local file-name clocks (`ops_query::compact_utc_now` versus `ops_file` / `sysdb::clock`; changing file names is a visible change); REST `/show`'s own directory scan (`handle_show` lists any `<name>.db` directory, also one holding no database; it should use `sysdb::database_dirs` plus the storage check like `/api show`); the `not_loaded` answers of `ops_db` and `ops_reason` (the differing codes are deliberate upstream parity, pinned by `dt_gapi_core::query_on_missing_or_unloaded_databases`); the two console pages (`server.rs` and `http_api.rs`, deliberately different; a mode flag would merge them); the hand-written HTTP clients (`http_client.rs`, `console/client.rs` — only the latter decodes chunked) and `gnlqa`'s own HTTP server (`gnlqa/src/http_server.rs`); for the test clients see tests-a#16 (J.15). (r4-api-hygiene)
- **sec#6, robust#9** (M8 follow-up; D3) — `http_client` keeps two URL splitters: `parse_http_url` (SERVICE, `http://` only) and `parse_url` (callbacks, downloads). Both refuse whitespace and control characters, but `parse_http_url` does not accept IPv6 literals (`http://[::1]:p/`) or a query without a path (`http://h?x`), does not strip a fragment and does not refuse user info. Folding SERVICE onto `parse_url` (keeping `https://` refused for SERVICE) is a small refactor. (r1-crash-dos)

### J.9 Concurrency and `ConcurrentDb`

- **design#14** (D2 / D3) — `concurrent::ConcurrentDb` is a second, library-only concurrency model next to the servers' single-writer `DbCell` + `/begin` transactions (its own OCC, isolation levels, version chains and publication path); kept and fixed. Merging the two models, or building the servers' multi-writer transactions (§I.1 D14) on it, is a design decision left open. (r4-concurrent)
- **conc#2, http#8** (partial, memory half; D3) — the version chains keep one record for every key whose committed state differs from the construction-time base snapshot, for the wrapper's life (`version_chain_stats().chains`). Folding them needs re-basing (replace the base with a newer published snapshot once no pin is below it, drop the folded chains); that changes what `VersionView::query` reads and would make version views see legacy `update()` / `write()` writes, which they do not today. The GC cost was the defect and is fixed; the memory is documented. (r4-concurrent)
- **conc#2** (observation) — `VersionView::query` materializes the base snapshot plus every chain on each query (O(base + chains)); point reads (`VersionView::contains`) clone nothing. Documented on the method. (r4-concurrent)
- **conc#2** (follow-up, dictionary) — the interner copy on the first brand-new term after a publish: merged into the first bullet of §I.5. (r4-concurrent)
- **conc#15** (observation) — `ConcurrentDb`'s snapshot and version-view queries take no cancel flag, so their CSR builds cannot be cancelled (the servers' read paths can since round 2); its CSR provider still builds with the uncancellable `CsrGraph::build` and could use `CsrGraph::build_from_memory` with the request's flag. An API addition, not a defect of the existing contract. (r4-concurrent, r2-index-cancel)
- **conc#9** — a statistics refresh is cancelled at pass granularity (`subject_num`, `type_statistics`, `schema_graph` have no internal checks), and "skip starting a refresh while a writer waits" is not done (the standard `RwLock` exposes no waiting-writer count). A refresh whose data changed between passes is dropped and the next `monitor` starts another, so under a steady stream of writes the `monitor` / `schema` statistics may stay those of earlier data until the writes pause; falling back to all three passes under one guard after a few dropped attempts would bound that. (r2-index-cancel)
- **conc#5, conc#14** — a statement that does not poll its cancel flag still delays its own database's final save at shutdown (the shutdown waits rather than skip the save: no data loss), as in §I.1 D10. Worker threads still serving a connection after 2 s are left detached and logged; `ShutdownReport` has no field for them. (r2-index-cancel)

### J.11 RDF readers

- **parser#18** (partial; D5) — the W3C rdf-tests (Turtle / TriG / N-Triples / N-Quads / RDF/XML syntax suites) and the official SPARQL 1.1 manifests are not vendored: D5 replaces them with hand-authored SPARQL cases (`tests/w3c`), and the machine had no reliable access to w3.org / GitHub. ### J.12 Experimental cluster (frozen, D4)

- **cluster-nlqa#9, sec#19, conc#11** (partial; D4) — fixed: no preallocation from a peer's length, read timeouts, oversized replies reported. Remaining: no authentication of shard or Raft RPCs (any client reaching the port can read, `ClientWrite` deletes, or send a plausible-term `InstallSnapshot` replacing a replica's store); one thread per connection with no cap or worker pool; `ShardNode::serve_forever` spins on persistent accept errors at the fd limit (`incoming().flatten()`; a connection cap fixes both); `ClusterNode::run_server` polls `accept` every 2 ms; `store.lock().unwrap()` in `dispatch` lets one panic poison a shard for every connection; `RemoteShard` holds one connection mutex across each round trip (callers to one shard serialize) and retries once on a fresh connection, so an `Insert` whose response was lost reports "not inserted" (needs idempotency tokens). *Reason:* authentication and the connection model are a redesign of a frozen experimental transport. (r5-cluster)
- **cluster-nlqa#2** (D4) — the term bound (2^32) is per message: it stops the one-message wedge, but a few forged plausible-step messages can still move one node more than 2^32 terms past its peers, which then refuse its messages and it theirs — cut off for good (durable with `--state-dir`). Any bound short of authenticated peer RPCs leaves a variant. (r5-cluster)
- **cluster-nlqa#1** (D4) — a member whose endpoint is gone for good cannot be evicted while it has stranded buckets (every membership change resumes them first), so membership is frozen until the node returns; an explicit "forget node, accept the loss" operation is missing. - **cluster-nlqa#12** (partial; D4) — the wrong-contract test was corrected; wall-clock assertions remain in `raft_tests::a_hung_peer_does_not_stall_the_healthy_majority` (commit in < 250 ms, no churn for 1.5 s) and `rpc::tests::loopback_round_trips_are_not_throttled_by_delayed_ack` (< 1500 ms); `ShardNode::serve_forever` has no shutdown, so test shard threads never stop; there are no tests for self / duplicate peers (cluster-nlqa#7), `gnode`'s `load_id_triples` / peer parsing, or the write-side `MAX_FRAME` check (needs a 256 MiB payload). - **cluster-nlqa#11** (D4) — the raft journal is never compacted (the transport never compacts its log either); config-change entries and snapshots still interact as the module docs describe; `gnode` shard mode keeps its data in memory. (r5-cluster)
- **cluster-nlqa#5, cluster-nlqa#6, cluster-nlqa#7, cluster-nlqa#8** (deferred; D4) — membership changes never alter the voter set; unbatched AppendEntries (catch-up stalls past `MAX_FRAME`); the own id / duplicate peers inflate the quorum; `DefaultHasher` placement across processes. Unchanged; reasons in J.1. (plan, r5-cluster)
- **parser#8** (D4) — `gnode` does not call `install_storage_defaults`, so its SPARQL requests have no `sparql_max_size` (the in-place tokenizer still removes the 12x amplification); only `gserver` and `gbuild` install the limits. (r3-parser)

### J.13 gNLQA

- **cluster-nlqa#13** — the rate limiter keys on the TCP peer address (IPv6: its /64), so behind a reverse proxy all clients share one bucket (no trusted-proxy setting; use the proxy's own limits); the per-client connection cap uses the same key and must be raised behind a proxy (`with_max_conn_per_client`; there is no environment key for it or for `max_conn`). A client with more addresses than the cap allows for (e.g. the /64s of an IPv6 /48) can still hold every slot with idle connections, each for up to the 30 s read deadline; a separate shorter deadline for the request head and an accept-rate limit per network would narrow that. While every one of the 10,000 tracked clients is limited, new clients share one overflow bucket (no client is ever reset). (r5-gnlqa)
- **cluster-nlqa#22** — the linker cache's KB fingerprint (two `COUNT`s) does not see a change that keeps the number of `rdfs:label` and `rdf:type` triples (e.g. a new predicate without labels or types); the one-day maximum age bounds that staleness, and deleting the cache directory forces a rebuild. (r5-gnlqa)
- **cluster-nlqa#21** — the optional stricter mode that sends no KB-derived text at all (no labels or schema samples) was not added; structured mode's documentation states exactly what it sends. (r5-gnlqa)
